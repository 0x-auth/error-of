Construct and error-of

A cue goes in, a frozen model proposes, the fabric runs it, error-of reads what happened, and only the last two errors are carried into the next try.

judgment errors and memory given by the fabric dashed line = slow path

How to read it

The solid loop is one walk. Each failed try leaves only two things behind: the last two errors. They go back to the reconstructor, which proposes again, until the gate passes.

The dashed loop is slow. Every run lands in error-of's case store. Over many runs, those cases are the events that shape the reconstructor. This is memory as a model trained by many events.

What error-of already gives

  • Capture under the fabric's limits, classified as boundary, assumption, invariant and transformation.
  • Memory and Time as error classes, with stream or chunk and cache or reduce as transformations. That is the space and time trade.
  • A heal is accepted only if its invariant holds. That is the gate.

Where it could go differently

  1. Errors carry the wall, not the side. Elimination needs a direction: too high or too low, too big or too slow. A side field on each case would feed the two edges directly.
  2. The rule table is written by a person. Good as a seed. Over time the outcomes in the case store should outrank the regex rules.
  3. The store records but does not learn yet. It does not rank which transformation worked for a signature. That ranking is the dashed arrow, and the smallest change with the biggest effect.
  4. Heal changes input, the loop changes programs. Keep error-of as observer and judge, and put the reconstructor outside it, instead of loosening that rule.
  5. The gate is the single point of failure. A wrong invariant steers every walk wrong. Two independent invariants that must agree would guard it.
